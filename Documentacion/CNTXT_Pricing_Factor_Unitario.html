El problema actual

Por qué el pricing actual dificulta cotizar proyectos de distinto tamaño

❌ Hoy — servicios con magnitud fija

Cada servicio tiene un precio y unas horas calculadas para una escala específica que no siempre coincide con el proyecto en cuestión.

D1.4 — Planimetría Urbanismo
// "hasta 15 ha" → 36.9 h → $3.482.633

Llega proyecto de 30 ha → ¿cuánto cobra?
❌ No hay respuesta automática

• El equipo ajusta a mano sin método claro
• Cotizaciones inconsistentes entre proyectos
• Se necesita crear múltiples versiones del mismo servicio

✅ Propuesta — unidad base + factor

Cada servicio se expresa como costo por 1 unidad. Al crear el cronograma, el usuario ingresa la cantidad del proyecto y el sistema calcula todo.

// unidad base: 1 ha → 2.46 h/ha → $232.176/ha

Llega proyecto de 30 ha:
✅ 30 × 2.46 = 73.8 h → $6.965.280

• Un solo servicio, infinitas escalas
• Cotización automática en 1 clic
• Trazabilidad y consistencia total

Concepto: APU aplicado a servicios de diseño

Igual que en los presupuestos de construcción, pero para horas de trabajo creativo

🏗️
¿Qué es un APU (Análisis de Precios Unitarios)?

En construcción, el APU calcula el costo de una unidad de trabajo (ej: 1 m² de piso). Multiplicado por la cantidad del proyecto da el costo total. La misma lógica aplica a servicios de diseño: si sabemos cuántas horas toma diseñar 1 ha de urbanismo, podemos cotizar cualquier proyecto urbanístico multiplicando por la superficie real.

// FÓRMULA GENERAL
Horas del proyecto = horas_por_unidad × cantidad_proyecto
Costo del proyecto = cop_por_unidad × cantidad_proyecto

// EJEMPLO D1.4 — Planimetría Arquitectónica del Urbanismo
horas_por_unidad = 36.9 h ÷ 15 ha = 2.46 h/ha
cop_por_unidad = $3.482.633 ÷ 15 = $232.176/ha

// Proyecto A — 10 ha
horas = 2.46 × 10 = 24.6 h costo = $232.176 × 10 = $2.321.760
// Proyecto B — 30 ha
horas = 2.46 × 30 = 73.8 h costo = $232.176 × 30 = $6.965.280
// Proyecto C — 15 ha (referencia original)
horas = 2.46 × 15 = 36.9 h costo = $232.176 × 15 = $3.482.640 ✓

Flujo en el aplicativo — cómo se vería

Pasos desde el maestro hasta el cronograma del proyecto

1

Maestro de Servicios — se define la unidad base y el valor unitario

Cada ServiceTemplate tiene dos nuevos campos: unidad_base (texto: "ha", "m²", "proyecto", "und") y cantidad_referencia (el número desde el cual se calculó el precio original). El sistema calcula y muestra automáticamente horas/unidad y COP/unidad.

2

Perfil del proyecto — se registra la magnitud

Al crear o editar el proyecto, el usuario registra las magnitudes clave: área de urbanismo (ha), área de edificación (m²), número de unidades complementarias, etc. Estos valores quedan disponibles para todos los servicios del cronograma.

3

Agregar servicio al cronograma — se aplica el factor

Al agregar un servicio al cronograma del proyecto, el sistema pre-llena automáticamente la cantidad con el valor registrado en el perfil del proyecto (ej: 22 ha). El usuario puede ajustarlo. Las horas, días y costo se recalculan en tiempo real.

4

Cronograma — resumen con totales automáticos

El cronograma muestra el desglose por servicio con su cantidad aplicada, y los totales de horas y costo del proyecto se actualizan en tiempo real. El valor total del proyecto se sincroniza automáticamente con el perfil del proyecto.

Cambios mínimos en el modelo de datos

Solo dos campos nuevos en ServiceTemplate + uno en WorkSchedule

# apps/services/models.py
class ServiceTemplate(TimeStampedModel):
    # ... campos existentes ...
    code = CharField(max_length=20)
    name = CharField(max_length=255)
    estimated_hours = DecimalField() # horas totales (referencia)
    base_unit_price = DecimalField() # precio total (referencia)
    # ── NUEVOS ───────────────────────────────────
    unit_label = CharField(max_length=30, default="proyecto")
        # Ej: "ha", "m²", "und", "proyecto", "video"
    unit_quantity_ref = DecimalField(default=1)
        # Ej: 15 si el precio fue calculado para 15 ha

    # @property calculados (no requieren migración adicional)
    @property
    def hours_per_unit(self):
        return self.estimated_hours / self.unit_quantity_ref
    @property
    def cost_per_unit(self):
        return self.base_unit_price / self.unit_quantity_ref

# apps/services/models.py (o projects/models.py)
class WorkSchedule(TimeStampedModel):
    # ... campos existentes ...
    service = ForeignKey(ServiceTemplate)
    planned_hours = DecimalField() # horas ajustadas por proyecto
    planned_cost = DecimalField() # costo ajustado
    # ── NUEVO ────────────────────────────────────
    unit_quantity = DecimalField(default=1)
        # Cantidad real del proyecto (ej: 22 ha)
        # planned_hours = service.hours_per_unit × unit_quantity
        # planned_cost = service.cost_per_unit × unit_quantity
✅
Compatibilidad total con lo existente

Todos los servicios que hoy tienen unit_quantity_ref = 1 (la mayoría de V.sual y servicios "por proyecto") funcionan exactamente igual que antes. El cambio solo aplica cuando unit_quantity_ref ≠ 1. No hay cambios en la lógica de fechas, Gantt ni notificaciones.

Impacto en el negocio

Qué resuelve esta metodología en la operación diaria de CNTXT

⏱️

Cotización en 1 clic

El liderazgo ingresa las magnitudes del proyecto (ha, m², unidades) y obtiene el presupuesto completo de honorarios en segundos, sin hojas de cálculo paralelas.

📊

Consistencia entre proyectos

El mismo criterio para todos: un proyecto de 8 ha siempre cuesta lo mismo por hectárea. Elimina las discrepancias entre cotizaciones de distintos líderes.

🎯

Trazabilidad de márgenes

Al tener el costo por unidad, el sistema puede comparar en tiempo real el margen proyectado vs. ejecutado por servicio y por fase del proyecto.

🔄

Actualizaciones masivas fáciles

Si cambia el costo de un rol (ej: +10% anual), basta actualizar el honorario en el maestro y todos los servicios se recalculan automáticamente.

📈

Datos para el dashboard

Con cantidades reales registradas, el dashboard puede mostrar indicadores como "costo promedio por m²" o "desviación en h/ha" entre proyectos similares.

🧩

Un maestro, múltiples escalas

Se elimina la proliferación de variantes del mismo servicio (Urbanismo 5ha, Urbanismo 15ha, Urbanismo 30ha). Un solo servicio, el factor lo resuelve todo.

Nota sobre V.sual

Los servicios V.sual tienen unit_quantity_ref = 1 porque son productos empaquetados (un pack de imágenes, un video, una web). Si en el futuro quieren escalar por cantidad de renders o de páginas, se puede ajustar el factor individualmente sin tocar la estructura.
